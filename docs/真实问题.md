## REAL-001：压缩时可能一次发送远超模型窗口的内容

### 通俗描述

项目本来想通过“总结旧对话”减少上下文，但它可能先把非常长的历史一次性全部
发送给负责总结的模型。

也就是说：

```text
正是因为历史太长，所以需要压缩
→ 压缩前却先把全部长历史交给摘要模型
→ 摘要请求本身先超过模型窗口
```

### 实测结果

测试配置的输入窗口：

```text
64,000 tokens
```

实际构造出的摘要请求：

```text
1,425,239 字符
约 356,309 tokens
```

### 影响

- 摘要请求可能直接失败；
- 会话越长，越容易无法压缩；
- 最需要压缩的时候，压缩功能反而最容易不可用；
- 可能产生一次非常昂贵的模型请求。

### 根因

主模型的上下文预算只约束了正常对话请求，没有同时约束 Summary Provider 的
输入。压缩器选出旧消息后，直接把全部旧消息拼成一个摘要请求；它既没有在调用
摘要模型前重新计算请求大小，也没有超限后的分块与归并流程。

因此，问题不在某个窗口数值设置得太小，而在于摘要链路缺少完整的输入预算契约。

### 解决方案

摘要链路现在使用与模型窗口一致的硬预算，执行过程变为：

```text
待压缩历史
→ 按摘要请求的可用输入预算分块
→ 分别生成局部摘要
→ 对局部摘要继续按相同预算分组归并
→ 得到一份最终摘要
```

具体保证如下：

- 每一次真实 Summary Provider 调用前都重新估算完整请求，超限就不发送；
- 单条旧消息本身过大时，也会按可容纳的最大前缀继续拆分，不会整条丢弃；
- 多个局部摘要仍然过大时，继续分层归并，而不是再次一次性发送；
- 摘要输出预算受模型预留输出空间约束，防止中间摘要持续膨胀，保证归并可以收敛；
- 最终仍只写入一份活动摘要，原有事务提交和恢复语义保持不变。

这修复的是“所有摘要请求都必须受窗口约束”这一通用逻辑，不依赖本次测试使用的
消息数量或具体窗口大小。

### 验证证据

自动化压力测试使用 30 轮长消息和 2,000-token 输入窗口：

- 摘要过程实际产生多次分层调用；
- 每次摘要请求都不超过 1,600-token 可用输入预算；
- 28 轮待压缩历史的唯一标记全部进入过摘要输入，没有静默漏掉整轮消息；
- 压缩成功后只存在一份活动摘要。

真实 Provider 测试使用隔离的临时 SQLite 数据库、项目实际 Provider 配置和
12 轮长对话：

```text
摘要调用次数：3
各次输入估算：5,692 / 5,693 / 685 tokens
摘要可用输入上限：6,000 tokens
压缩前：13,375 tokens
压缩后：2,697 tokens
提交状态：committed
活动摘要：1
SQLite integrity_check：ok
```

此外，全量自动化回归为 `114/114 PASS`。

### 当前状态

已于 2026-08-23 完成根因修复，并通过自动化压力测试、全量回归和真实 Provider
分层摘要测试。REAL-001 已关闭。

## REAL-002：部分密钥无法被摘要脱敏识别

### 通俗描述

项目在总结历史前会隐藏一部分密码和 API Key，但它主要识别下面这些带标签的
格式：

```text
api_key=xxx
password=xxx
token=xxx
Bearer xxx
```

如果密钥直接出现在正文中，没有 `api_key=` 等字段名，就可能识别不出来。

### 实测结果

测试在历史中放入：

```text
sk-proj-UNLABELED_SECRET_ABC123
```

捕获到的 Summary Provider 请求中仍然包含完整字符串。

### 影响

- 裸 API Key 可能被发送给摘要模型；
- 私钥、URL 查询参数和其他未标注凭据也可能遗漏；
- 用户以为压缩前已经脱敏，实际并不完整。

### 根因

原来的脱敏逻辑只有两类正则：一种匹配 `Bearer ...`，另一种只匹配带字段名的
`api_key=...`、`token=...`、`password=...` 和 `secret=...`。它把“凭据旁边是否
有标签”误当成了“内容是否是凭据”，没有识别密钥自身的结构，也没有统一处理
私钥块、JWT、Authorization Header 和 URL 中的凭据。

因此 `sk-proj-...`、`github_pat_...` 等即使可以从自身格式明确判断为凭据，只要
前面没有受支持的字段名，仍会原样进入 Summary Provider 请求。

### 解决方案

新增集中式摘要边界脱敏器，所有进入摘要模型的历史内容和所有摘要模型返回的内容
都经过同一个识别入口。识别不再只依赖标签，而是由几类互补规则组成：

- 敏感字段：环境变量、JSON、YAML 和查询参数中的 `api_key`、`access_token`、
  `client_secret`、`password` 等；
- 自描述凭据：OpenAI、GitHub、Slack、Google、AWS、Stripe、SendGrid 等具有明确
  前缀和最低长度的密钥；
- 结构化凭据：完整 JWT、PEM 私钥块、Authorization Header；
- URL 凭据：`scheme://user:password@host` 和 URL userinfo 中的裸 token；
- 统一替换为不可复用的 `[REDACTED]`，不保留密钥头尾片段。

规则使用明确的格式和最低长度，而不是把所有长字符串都判为密钥。敏感字段必须
出现在键名末尾，所以 `SERVICE_REFRESH_TOKEN=...` 会被隐藏，但 `token_count=42`、
`session_id=...` 和文档里的 `sk-example` 不会被误删。这是在泄漏防护和历史语义
完整性之间设置的明确边界。

需要注意：没有字段名、没有已知格式、也不具备可识别结构的任意随机字符串，单靠
文本无法可靠判断是不是秘密；强行按“高熵字符串”全部删除会误伤哈希、ID 和源码。
本次修复关闭的是已复现的自描述密钥及上述结构化凭据漏洞，而不是宣称能猜出所有
未知格式的秘密。

### 验证证据

自动化测试新增 4 组脱敏契约，并扩展真实压缩流程测试，覆盖：

- 无字段名的 `sk-proj-...`、GitHub、Slack、Google、AWS、Stripe 和 JWT；
- JSON/环境变量敏感字段、Basic Authorization、URL 密码和查询 token；
- 完整 PEM 私钥块；
- `token_count`、`session_id`、短示例 key 等误报保护；
- Summary Provider 输入与返回摘要的双向脱敏。

真实 Provider 测试使用隔离的临时 SQLite 会话，把 OpenAI 风格 key、GitHub PAT、
JWT、私钥正文、URL 密码和 URL 查询 token 共 6 个唯一诱饵放入待压缩历史：

```text
压缩状态：committed
真实 Summary Provider 调用：3 次
进入 Provider 的原始诱饵：0
提交后活动上下文中的原始诱饵：0
各次请求中的 [REDACTED] 数量：6 / 0 / 5
SQLite integrity_check：ok
```

全量自动化回归为 `118/118 PASS`。

### 当前状态

已于 2026-08-23 完成根因修复，并通过自动化边界测试、完整压缩流程、真实 Provider
测试和全量回归。REAL-002 已关闭。

## REAL-003：压缩后可能比压缩前更长，却仍显示成功

### 通俗描述

系统现在判断“压缩成功”的主要标准是数据库事务是否成功写入，而不是是否真的
减少了上下文。

因此摘要写入成功，即使内容变得更长，也会显示 `committed`。

### 实测结果

```text
压缩前：约 138 tokens
压缩后：约 1,643 tokens
结果：committed
活动 Summary：1 份
```

压缩后大约变成原来的十多倍。

### 影响

- 一次“成功压缩”可能增加后续模型成本；
- Prompt Cache 会因为一次没有收益的压缩而失效；
- 用户和日志看到成功，但实际上没有达到压缩目的；
- 当前低收益熔断只能在提交后统计，不能阻止这次负收益提交。

### 根因一：为什么摘要可能比原历史更长

摘要输出预算依据整个模型窗口和 `target_ratio` 计算，却没有依据“本次压缩至少必须
节省多少 token”计算。更关键的是，旧逻辑为了兼容推理模型，给摘要输出设置了最高
可达 1,024 tokens 的强制保底。

因此，即使真正被替换的中间历史很短，Summary Provider 仍可能获得远大于这段历史
的输出额度。摘要正文再加上固定的 summary wrapper、首尾保护消息和 bridge 后，新的
上下文自然可能比原上下文更大。

### 根因二：为什么仍然显示成功

旧流程先归档原消息并插入摘要，然后才计算收益：

```text
saved_tokens = max(0, before_tokens - after_tokens)
```

如果压缩后更长，真实收益本应是负数，但 `max(0, ...)` 会把它改写成 0。数据库随后
仍插入一条 `committed` 记录；低收益计数只用于若干次以后暂停自动压缩，无法阻止本次
负收益结果破坏活动上下文。CLI 展示时又对收益做了一次 `max(0, saved)`，用户连负数
也看不到。

### 解决方案

现在建立了贯穿生成、提交和存储的硬收益契约：

```text
required_savings = max(1, ceil(before_tokens × min_savings_ratio))
只有 before_tokens - after_tokens >= required_savings 才能 committed
```

具体分为四道约束：

1. **生成前动态预算**：先计算 system、受保护 head/tail、summary wrapper、bridge 和
   tool schema 的固定成本，再根据本次允许的最大 `after_tokens` 推导摘要输出额度；
   删除与被压缩内容无关的 1,024-token 强制保底。
2. **提交前实际复算**：Summary Provider 返回后，使用最终摘要和完整新消息重新估算；
   不满足最低收益就返回 `rejected`，不归档任何原消息。
3. **数据库事务硬校验**：`archive_and_compact()` 在执行第一条归档 SQL 之前再次验证
   最低节省量。即使未来某条调用路径绕过管理器，也不能写入负收益 `committed`。
4. **真实状态与防抖**：被拒绝的候选记录为失败审计，错误类型为
   `InsufficientCompressionSavings`；连续低收益会进入 cooldown 并按原有阈值自动暂停。
   CLI 不再把负收益强制显示为 0。

`target_ratio` 现在是软目标：如果受保护的 head/tail 本身已经超过目标，就不能为了
追求不可实现的目标而不给摘要任何空间；此时以最低收益硬契约为准。无论软目标能否
达到，负收益都绝不允许提交。

### 验证证据

重新执行原始膨胀场景，Summary Provider 固定尝试返回约 6,000 字符：

```text
修复前：338 → 1,621 tokens
修复前收益：-1,283 tokens
修复前状态：committed

修复后动态输出额度：81 tokens
修复后：338 → 304 tokens
修复后收益：34 tokens（达到 10% 最低要求）
修复后状态：committed
```

这说明正常路径不是简单把失败改名，而是从源头约束摘要，使它真正产生收益。

故障注入还强制绕过生成预算，构造负收益候选：

- 管理器返回 `rejected` 和 `InsufficientCompressionSavings`；
- 活动消息在拒绝前后逐项完全一致；
- 连续两次低收益候选会触发 `auto_paused`；
- 直接绕过管理器调用数据库提交，也会在归档前收到 `SessionError`；
- 没有活动消息被归档，没有压缩摘要被写入。

真实 Provider 测试使用项目实际模型配置和隔离的临时 SQLite 长会话：

```text

压缩前：11,161 tokens
压缩后：2,230 tokens
实际节省：8,931 tokens
节省比例：80.02%
状态：committed
活动消息：24 → 6
SQLite integrity_check：ok
```

全量自动化回归为 `122/122 PASS`，其中包含 CLI 必须显示 `status=rejected` 和真实
负收益值、不能再显示成功或把负数改成 0 的输出契约测试。

### 当前状态

已于 2026-08-23 同时修复“摘要为什么会膨胀”和“负收益为什么仍会成功”两个根因，

Provider 测试和全量回归。REAL-003 已关闭。

## REAL-004：大文件只能读取开头，后半部分无法继续读取

### 通俗描述

文件工具读取大文件时会截断内容，但没有提供“从上次位置继续读”的功能。

模型即使知道文件被截断，也没有办法读取后半部分。

### 实测结果

测试文件约 25,000 字符，关键标记放在文件末尾：

```text
Tool Result 长度：约 11,992 字符
truncated：true
末尾关键标记：不可见
```

`read_file` 本身最多取 20,000 字符，Registry 的结果预算又把最终结果限制到
约 12,000 字符。

### 影响

- Agent 可能只能审查大型源码文件的前半部分；
- 文件末尾的函数、配置和错误无法获取；
- 模型可能在没有读完整文件的情况下给出完整审查结论；
- 重复调用相同 `read_file` 仍然只会得到同一个开头。

### 根因

这是两个独立截断机制叠加形成的问题：

1. `read_file` 固定返回文件开头最多 20,000 个字符，参数中没有起始位置，也没有
   返回下一页游标；再次调用只能重新读取开头。
2. Tool Registry 还有默认 12,000 字符的统一结果预算。文件工具返回的结构超过预算
   后，Registry 会把整个 `result` 替换为通用 `preview`。这样不但正文再次被截断，
   连文件工具原来的 `path` 和 `truncated` 等结构化信息也会消失。

所以只给 `read_file` 增加一个更大的固定上限并不能解决问题：文件仍可能更大，Registry
仍可能二次截断，而且模型依然不知道从哪里继续。

### 解决方案

`read_file` 现在使用显式、可验证的分页协议：

- `offset`：本页从文件的第几个 Unicode 字符开始，默认 0；
- `limit`：本页最多请求多少字符，范围为 1 到 20,000；
- `returned_chars`：本次实际返回的字符数；
- `next_offset`：下一次调用应使用的准确位置，读完时为 `null`；
- `total_chars`：本次读取看到的文件总字符数；
- `eof`：是否已经到达文件末尾；
- `truncated`：为兼容旧调用保留，含义为当前页后面仍有内容；
- `revision`：完整文件内容的 SHA-256 版本标识。

模型按照下面的协议读取即可：

```text
第一次：read_file(path)
后续：read_file(path, offset=next_offset, expected_revision=revision)
直到：eof=true
```

`expected_revision` 用来解决分页期间文件发生变化的问题。如果第一次读取后文件被
修改，后续调用会返回明确的 `tool_input_error`，要求从 offset 0 重新开始，而不是把
两个版本的文件静默拼接在一起。

Registry 的结果预算也改为识别这种可续读文本页：

## REAL-005：默认线程工具超时后仍可能继续产生副作用

### 通俗描述

有些工具超时后，Agent 已经收到“工具超时”，但工具其实还在后台继续运行。

### 实测结果

测试工具被设置为延迟写文件：

```text
0.1 秒：Harness 返回 tool_timeout
返回时：文件不存在
0.7 秒后：文件真实出现
hard_terminated=false
effect_disposition=unknown
```

### 影响

如果超时工具负责：

- 发消息；
- 修改文件；
- 创建订单；
- 调用外部服务；

那么 Agent 可能已经开始恢复或执行下一步，而旧工具随后又产生真实副作用。

内置文件和 Memory 工具使用可终止的 Spawn 后端；该问题主要影响使用默认线程
后端的自定义工具。

### 根因

Registry 原来把 `ThreadExecutionBackend` 作为所有未指定后端工具的默认值。线程
超时时调用：

```python
future.cancel()
executor.shutdown(wait=False, cancel_futures=True)
```

但 Python 的 `Future.cancel()` 只能取消尚未开始的任务；Handler 一旦进入运行状态，
Python 没有安全强杀该线程的机制。`shutdown(wait=False)` 只是不再等待，并不会停止
线程。因此 Harness 返回 `tool_timeout` 后，Handler 仍持有原来的文件、网络客户端或
服务对象，可以在后台继续产生副作用。

这不是增加一次 `cancel()`、缩短 timeout 或在线程外再包一层状态检查能解决的问题；
“可以硬终止”和“必须共享当前进程内状态”是两种不同执行模型，必须显式区分。

### 解决方案

现在采用下面的执行契约：

1. **默认使用 Spawn 隔离进程**：`ToolRegistry` 未显式指定后端时使用
   `SpawnProcessExecutionBackend`。超时后父进程会 terminate，必要时再 kill，并等待
   子进程退出后才返回 `tool_timeout`。
2. **序列化失败不偷偷降级**：Spawn 执行前使用 multiprocessing 的实际序列化器验证
   Handler。闭包等不可序列化对象返回 `execution_start_error / HandlerNotSerializable`，
   且 `handler_started=false`，不会为了兼容性静默退回无法强杀的线程。
3. **Thread 后端不再伪造超时**：必须共享进程内状态的工具仍可显式选择
   `ThreadExecutionBackend`。因为线程不能安全终止，它会等待 Handler 真正成功或失败
   后再返回；需要硬截止时间的工具不能选择 Thread。
4. **副作用状态继续保守**：`hard_terminated=true` 只证明隔离进程已经停止，不能证明
   Handler 在超时之前没有做过部分操作。因此副作用工具的 `effect_disposition` 和
   Journal 状态仍是 `unknown`，Agent 不会自动重试。

这个修复没有把未知结果伪装成“绝对没有副作用”。它保证的是：Harness 返回以后，
超时 Handler 本身不再继续运行；至于超时前已经发生了什么，仍按原有恢复协议检查。

### 验证证据

使用真实 Tool Registry、默认后端和临时文件，重新运行“延迟 0.5 秒写文件、超时
0.1 秒”的原始场景：

```text
默认后端：spawn_process
返回耗时：约 0.34 秒（包含 Windows Spawn 启动和终止）
结果：tool_timeout
hard_terminated：true
返回时文件存在：false
再等待 0.55 秒后文件存在：false
```

对显式 Thread 兼容路径运行相同 Handler：

```text
显式后端：thread
配置 timeout：0.1 秒
实际返回耗时：约 0.52 秒
结果：success
返回时副作用已经完成：true
```

这说明 Thread 不再出现“0.1 秒先报超时，0.5 秒后才写文件”的分裂状态。

自动化测试还覆盖：

- 默认 Registry 的延迟副作用在返回后和额外等待后都不存在；
- 默认超时元数据为 `spawn_process + hard_terminated=true`；
- 不可序列化闭包在 Handler 入口前失败，捕获的本地副作用列表保持为空；
- Thread 超过期限后等待真实完成并返回成功；
- Agent、Tool Result 和 SQLite Journal 全链路记录默认 Spawn 的硬终止信息；
- 已显式使用 Spawn 的文件与 Memory 工具保持原有行为；
- 单元测试中确实需要观察进程内列表的 Handler 显式选择 Thread，不再依赖危险默认值。

全量自动化回归为 `128/128 PASS`。

已于 2026-08-24 完成默认执行模型和 Thread 超时语义的根因修复，并通过真实延迟
副作用测试、不可序列化 Handler 测试、Agent + Journal 端到端测试和全量回归。

## REAL-006：finalizer 失败会留下内部控制消息

### 通俗描述

Agent 达到工具或迭代上限时，会在内部添加一条消息，要求模型总结当前进展。

如果这次总结调用失败，这条内部消息仍然留在长期会话历史里。

### 实测结果

注入 finalizer Provider 故障后：

```text
AgentLoopError：finalization failed
活动消息：4 条
持久化 Harness control 消息：1 条
Resume 后最后角色：user
Resume 没有清理该消息
```

持久化内容类似：

```text
[Harness control] Tool execution has stopped...
```

### 影响

下次用户继续聊天时，模型可能同时看到：

```text
内部要求：总结上一次工作
真实用户要求：开始新的任务
```

内部控制消息可能干扰新任务，也可能与下一条真实 User 消息发生合并。

### 根因

`_finalize_without_tools()` 原来为 finalizer 构造 `[Harness control]` 后，调用了普通的
`_record_message()`。这个函数不仅修改本轮工作消息，还会立即将消息追加到 SQLite，
并更新 Agent 的长期 `_messages`。

执行顺序实际是：

```text
持久化 Harness control
→ 调用 no-tools finalizer
→ finalizer 成功后再持久化 Assistant 总结
```

因此控制消息是否落库与 finalizer 是否成功完全无关。Provider 抛异常、返回空文本、
或违规返回 Tool Call 时，后续 Assistant 消息不会产生，但已经提交的 User 控制消息
无法自动回滚，Resume 也无法判断它不是真实用户输入。

根本错误是把“仅用于一次 API 调用的控制协议”当成了“会话事实”。

### 解决方案

Harness control 现在被定义为 request-local 消息：

```text
长期 working_messages ────────────────┐
                                      ├→ 构造 finalizer 请求副本
临时 [Harness control] ───────────────┘

finalizer 失败 → 不写入任何控制消息
finalizer 成功 → 只把 Assistant 总结追加到长期历史
```

具体保证如下：

- 控制指令只通过新的 `request_messages` 列表发送给 no-tools finalizer；
- 不再调用 `_record_message()` 保存控制指令；
- finalizer 成功时，Assistant 总结直接追加到原来的 `working_messages`，保持真实角色
  顺序，例如 `assistant(tool_calls) → tool → assistant(summary)`；
- finalizer 失败时，已经持久化的 User、Assistant Tool Call、Tool Result 和 Journal
  证据全部保留，只有临时控制消息消失；
- `last_stop_reason` 和 `last_turn_completed=false` 在调用 finalizer 前就更新，因此即使
  finalizer 自身失败，Agent 仍能如实报告停止原因；
- context-budget finalizer 仍只收到稳定 System 和临时控制消息，不会重新暴露超预算
  历史，但该控制消息同样不会进入会话。

这里没有采用“失败后删除最后一条消息”的补丁。删除式恢复存在竞态，也可能误删
用户恰好并发写入的真实消息。正确逻辑是控制消息从一开始就不进入长期存储。

### 验证证据

重新运行真实 SessionDB、一次 Tool Call、`max_iterations=1` 和 finalizer Provider
异常的原始场景：

```text
结果：AgentLoopError(finalization failed)
修复前活动消息：4
修复后活动消息：3
持久化 Harness control：0
Resume 后最后角色：tool
SQLite integrity_check：ok
```

随后使用新的 Agent 和 Provider 恢复同一个 Session，并发送 `new real task`：

```text
恢复后的 Provider 请求中 Harness control：0
最新 User 内容严格等于 new real task：true
新一轮回答：new turn handled
```

成功 finalizer 路径也经过真实 SQLite 测试：finalizer 的 API 请求中仍包含临时
Harness control，但数据库和 Resume 历史只新增 Assistant 的部分完成总结。

自动化测试还验证了 `turn.finalization_failed` 事件只产生一次、失败后
`last_stop_reason=iteration_limit`，以及已有 context-budget 最小 finalizer 行为保持
不变。全量自动化回归为 `130/130 PASS`。

### 当前状态

已于 2026-08-24 完成 finalizer 控制消息生命周期的根因修复，并通过失败、成功、
Resume 新会话、context-budget 回归和全量测试。REAL-006 已关闭。

## REAL-007：摘要太慢时，同一 Session 可能重复调用摘要模型

### 通俗描述

压缩开始时系统会加锁，但生成摘要期间不会持续延长锁的有效期。

如果摘要模型响应太慢，锁可能先过期，另一个 Agent 就会认为可以开始第二次压缩。

### 实测结果

使用短锁时间和慢 Summary Provider：

```text
第一个压缩器：调用摘要模型
锁过期
第二个压缩器：再次调用摘要模型并提交成功
第一个压缩器：提交失败
Summary 调用总数：2
committed Run：1
failed Run：1
```

### 影响

- 同一个历史可能被摘要两次；
- 浪费一次模型调用；
- 留下一次不必要的失败记录；
- 高延迟时压缩结果不稳定。

默认锁 TTL 和 Provider timeout 都是 120 秒，因此临界延迟附近存在竞争窗口。

### 根因

原来的锁其实只是一张写着过期时间的“入场票”，不是覆盖整个压缩生命周期的
租约：

```text
获取锁 → 规划压缩 → 调用 Summary Provider（可能很慢） → 续期一次 → 提交
```

在 Provider 阻塞期间没有任何续期动作。第二个压缩器只看数据库的过期时间，
因此会合法地抢走锁并再调一次模型。

还有两个同类的底层语义错误：

- `refresh_compression_lock()` 只检查 owner，不检查锁是否已过期，使旧 owner
  可以把已过期但暂未被抢走的锁“复活”；
- `archive_and_compact()` 提交前只校验 owner，不校验租约是否仍在
  有效期内。

所以根因不是“TTL 设得太短”，而是系统没有把这把锁实现成真正的
可续期租约。

### 解决方案

压缩现在使用覆盖完整生命周期的租约协议：

```text
获取租约
  → 启动 watchdog，每 TTL / 3 续期
  → 每次 Summary Provider 调用前同步校验
  → Provider 阻塞时 watchdog 持续续期
  → Provider 返回后再同步校验
  → 数据库事务提交前校验 owner + 有效期
  → 停止 watchdog 并释放租约
```

该逻辑同时覆盖普通摘要、分层摘要的每一次 Provider 调用、fallback
和最终提交，不是只给当前测试的某一条路径延长 TTL。

租约如果真的丢失，旧压缩器会立即停止后续模型调用和提交，并且不会以
旧 owner 身份写入失败冷却记录，避免污染已经取得新租约的工作者。

底层数据库不再允许过期租约续期，并在任何归档 SQL 执行前校验租约的
owner 和过期时间。因此即使 watchdog 异常，过期工作者也不能改写活动历史。

### 验证证据

使用两个独立 `SessionDB`/SQLite 连接并发执行真实压缩，设置：

```text
租约 TTL：150 ms
第一个 Summary Provider 阻塞：300 ms（TTL 的 2 倍）
第二个压缩器：在 300 ms 后尝试压缩同一 Session
```

修复后结果：

```text
第二个压缩器状态：locked
第二个 Summary Provider 调用数：0
第一个压缩器状态：committed
Summary Provider 总调用数：1
压缩审计记录：1 条 committed，0 条 failed
SQLite integrity_check：ok
```

额外的过期租约测试确认：旧 owner 不能续活过期租约，也不能进入归档
事务，失败后活动消息 ID 完全不变。

全量自动化回归为 `132/132 PASS`。

### 当前状态

已于 2026-08-24 完成可续期压缩租约的根因修复，并通过真实并发压缩、
过期租约、事务防线和全量回归测试。REAL-007 已关闭。

## REAL-008：慢 Memory 更新可能导致陈旧锁误判和系统错误

### 通俗描述

Memory 锁超过一定时间后，会被认为是崩溃留下的垃圾锁。

但一次正常更新如果真的执行得很慢，也可能被误认为崩溃。

### 实测结果

测试让第一个 Memory 更新持续超过测试用 `stale_lock_seconds`，第二个更新尝试
删除锁文件。

Windows 返回：

```text
PermissionError
```

第一份更新随后正常完成。

### 影响

- 第二个更新得到底层系统错误，而不是统一 Memory 错误；
- 慢磁盘、网络目录或安全软件扫描可能增加发生概率；
- 用户难以判断是 Memory 冲突、权限问题还是文件损坏。

默认情况下要超过 60 秒才容易触发，发生概率低于其他问题。

### 根因

原实现把“锁文件存在了多久”错当成“持有锁的进程是否还活着”：

```text
发现 .memory.lock
  → 用 mtime 计算年龄
  → 超过 stale_lock_seconds
  → 直接 unlink 锁文件
```

但时间戳只能说明文件多久没修改，不能证明进程已经死亡。正常的慢磁盘写入、
网络目录和安全软件扫描都可能让一次更新超过阈值。

直接删除锁文件还具有平台相反但同样错误的后果：

- Windows 通常拒绝删除已打开的锁文件，泄漏底层 `PermissionError`；
- 允许删除已打开文件的系统会创建新 inode，新旧两个更新者可能同时
  认为自己持有锁。

因此这不是一个需要“抓住 `PermissionError`”的异常处理问题，而是用文件
时间戳实现进程互斥的基础语义错了。

### 解决方案

Memory 互斥现在改为操作系统内核管理的跨进程锁：

- Windows 使用 `msvcrt.locking(..., LK_NBLCK, 1)` 锁住第一个字节；
- POSIX 使用 `fcntl.flock(..., LOCK_EX | LOCK_NB)`；
- 竞争者使用单调时间等待到 `lock_timeout_seconds`，超时统一返回
  `MemoryStoreError`；
- 不再删除 `.memory.lock`。该文件只是稳定的锁载体，“文件存在”不再
  表示“正在被锁”；
- 正常退出时显式解锁，异常退出或进程崩溃时，内核会随文件描述符关闭
  自动释放锁；
- 打开锁文件或获取锁的其他系统错误被转换为统一的 `MemoryStoreError`，
  不再向 Tool 层泄漏平台异常。

`stale_lock_seconds` 参数和配置已删除。内核能直接判断锁是否仍被进程持有，
继续暴露这个无效阈值只会让用户以为系统仍在做时间戳推测。

### 验证证据

使用 Windows `spawn` 启动两个真实进程，第一个进程已获取 Memory 锁并停在
原子写入中：

```text
第一个更新持锁时间：> 300 ms
旧测试的陈旧阈值：200 ms
第二个更新等待上限：150 ms
第二个结果：MemoryStoreError(Timed out waiting...)
第二个更新是否写入：否
第一个进程在竞争后是否仍活着：是
释放后第一个结果：committed
最终 MEMORY.md：slow update committed
```

另一个真实进程在持锁后直接以 `os._exit(17)` 崩溃。进程结束后，新的
Memory 更新无需等待陈旧阈值便立即写入 `recovered immediately`。

回归测试还确认：仅有历史锁文件、但没有内核锁持有者时可立即恢复；活跃
持有者不会被抢占；遗留临时文件只在获得锁后清理。Memory 专项测试为
`10/10 PASS`，全量自动化回归为 `134/134 PASS`。

### 当前状态

已于 2026-08-24 用内核跨进程锁替代基于时间戳的陈旧锁猜测，并通过真实
慢更新竞争、进程崩溃恢复和全量回归。REAL-008 已关闭。

## REAL-009：超过 200 个目录项后，剩余项目无法查看

### 通俗描述

`list_files` 最多返回 200 项。超过后会告诉模型结果被截断，但没有“下一页”。

### 实测结果

```text
目录真实文件数：250
返回文件数：200
truncated：true
分页参数：不存在
```

### 影响

- 剩余 50 个文件对 Agent 不可见；
- 大型项目的文件发现不完整；
- Agent 可能错误地认为某个文件不存在；
- 递归目录列举更容易触发。

### 根因

`list_files` 原来的核心逻辑是：

```text
枚举并排序全部路径
→ 固定取 paths[:200]
→ 只返回 truncated=true
```

`truncated` 只说明“后面还有”，但结果里没有当前位置、下一页位置、总数和
目录版本。Tool Schema 也不接受任何续页参数，所以模型知道结果不完整，却没有
合法操作可以取得第 201 项。

还有第二个同类根因：工具注册表会按 `max_result_chars` 限制完整 JSON。即使只在
`list_files` 中加入分页，当单页文件名较长时，通用限长器仍会把结果换成
`preview`，导致新加的游标和 revision 再次丢失。

根本问题是目录列表被当成“可以丢掉后半部的普通文本”，而不是可续读、
可验证的数据快照。

### 解决方案

`list_files` 现在使用与大文件续读一致的分页合同：

- 请求参数增加 `offset`、`limit` 和 `expected_revision`；
- 结果返回 `offset`、`returned_entries`、`next_offset`、`total_entries`、
  `revision`、`eof` 和 `truncated`；
- 首页使用 `offset=0`，后续页必须携带首页的 `expected_revision`，并使用
  `offset=next_offset`；
- 排序键改为 `(casefold path, original path)`，避免仅大小写不同的名称出现
  不稳定顺序；
- revision 由相对目录、`recursive` 模式和完整排序后的路径/类型列表生成；
- 续页前如果文件被新增、删除或类型改变，revision 不匹配，工具会拒绝
  混合两个目录状态并要求从第 0 页重新开始；
- 结果限长器也识别目录页。如果请求的 200 项超过单次输出预算，它会
  缩少当前页的条目数，同时重新计算 `returned_entries/next_offset/eof`，
  不会降级成不可续读的 preview。

这里没有简单删除 200 项上限。无上限列举会把超大目录一次性塞入模型上下文，
将原来的“不可见”变成新的 Token 爆炸问题。可续读分页同时保证了完整性和
单次输出边界。

### 验证证据

先在临时目录中真实创建 250 个文件，修复前结果为：

```text
real_files：250
returned：200
truncated：true
result_keys：entries, path, truncated
```

修复后使用真实 `ToolRegistry` 和 Spawn Process 执行同一列举，并把单次结果预算
故意压到 2500 字符：

```text
目录文件数：250
完成页数：6
合并后条目数：250
唯一条目数：250
是否与真实排序目录完全一致：true
最后一项：file-249.txt
每次 Tool Result 是否 <= 2500 字符：true
是否出现 preview 降级：false
```

目录变化测试在第一页后真实新增文件，携带旧 revision 读取第二页时
得到 `tool_input_error: directory changed... restart at offset 0`。没有 revision 却直接使用
非零 offset 也会被拒绝，防止模型无意间混合两个快照。

全量自动化回归为 `136/136 PASS`。

### 当前状态

已于 2026-08-24 完成稳定目录快照、可续读分页和结果预算协同的根因修复，
并通过真实大目录、文件变化防护和全量回归。REAL-009 已关闭。

## REAL-010：Skill 调用会向外部模型发送本机绝对路径

### 通俗描述

Skill 完整加载后，发给模型的 User 消息中包含 Skill 在本机的完整路径。

例如：

```text
C:\Users\某个用户名\AppData\Local\Temp\...\skills\audit-skill
```

### 实测结果

真实 Provider Skill 调用成功返回指定标记，同时捕获的 Invocation 中确认包含
Skill 目录的绝对路径。

### 影响

- 可能泄露 Windows 用户名；
- 可能泄露磁盘和项目目录结构；
- 可能暴露公司、客户或项目名称；
- 这些路径会发送给外部模型 Provider。

### 根因

Skill 加载阶段确实需要本机绝对路径，因为 Harness 必须用它校验 Skill 没有逃离
可信根目录，并从磁盘读取完整 `SKILL.md`。问题不在“内部不应该有路径”，而在
这个只属于本地控制面的字段被复制进了模型数据面。

具体传播链为：

```text
SkillIndexEntry.skill_dir（本地路径）
→ LoadedSkill.skill_dir（本地路径）
→ build_invocation() 字符串插值
→ [Skill directory: C:\Users\...]
→ SkillInvocation.message
→ Agent.chat_with_skill()
→ Provider User message
```

原来的 `SkillInvocation` 数据类本身还包含 `skill_dir: Path`。这表明它混合了两种
安全级别不同的数据：本地文件系统定位信息，以及允许发送给 Provider 的调用内容。

这不是 Provider 或日志脱敏失败，而是 Skill 加载边界没有区分“主机私有定位”
和“模型可见标识”。

### 解决方案

Skill 路径现在在加载边界被明确分为两类：

```text
主机私有：Path(...)                     只用于发现、信任边界校验和读取文件
模型可见：skill://<source>/<name>/   只表示逻辑 Skill 根
```

具体保证如下：

- `SkillIndexEntry` 和 `LoadedSkill` 仍在本地保留 Path，因为安全加载真的需要它；
- 可以进入 Agent 调用链的 `SkillInvocation` 已删除 `skill_dir` 字段，从类型层防止
  后续代码再次误发；
- `SkillInvocation` 只保留由受控 source 和已校验 Skill name 生成的逻辑
  reference，例如 `skill://bundled/review/`；
- Provider 消息会告诉模型这是逻辑 Skill 根，不应猜测主机文件系统位置；
- `skill.loaded` 事件记录安全逻辑 reference，仍然不记录 Skill 正文、用户任务
  或本机路径。

这里没有对整条 User 消息做简单的路径正则替换。Skill 作者可能在正文中明确写入
任务必需的路径，用户任务也可能主动包含路径；无差别脱敏会篡改指令语义。
根因修复只移除 Harness 自己附加、且不应出站的主机元数据。

### 验证证据

修复前在临时目录创建真实 `audit-skill/SKILL.md`，通过 `Agent.chat_with_skill()`
发送给记录型 Provider：

```text
Agent 返回：done
Provider 是否收到 Skill 绝对路径：true
泄露样例：C:\Users\24657\AppData\Local\Temp\...\bundled\audit-skill
```

修复后重新执行同一条真实 Agent 调用链：

```text
Agent 返回：done
Provider 是否收到 Skill 绝对路径：false
Provider 是否收到临时根目录：false
Provider 是否收到 skill://bundled/audit-skill/：true
Provider 是否仍收到完整 Skill 正文：true
```

额外测试真实创建了配置的外部 Skill、内置 Skill 和显式启用的官方可选 Skill，
三者分别只暴露：

```text
skill://external/external-skill/
skill://bundled/bundled-skill/
skill://optional/optional-skill/
```

三类 invocation 均不包含临时根目录，且类型上已不再有 `skill_dir` 属性。
Skill 专项测试为 `11/11 PASS`，全量自动化回归为 `137/137 PASS`。

### 当前状态

已于 2026-08-24 完成 Skill 主机私有路径与模型可见引用的数据边界修复，并通过
三类 Skill 来源、真实 Agent 出站消息和全量回归。REAL-010 已关闭。

## REAL-011：不同 Profile 可以看到彼此的 Session 元数据

### 通俗描述

Profile 可以阻止直接恢复其他 Profile 的 Session，但列出 Session 时没有按当前
Profile 过滤。

### 实测结果

在同一数据库创建：

```text
alice-private-session，profile=alice
bob-private-session，profile=bob
```

调用 `list_sessions()` 同时返回两者，并显示：

- Session ID；
- Profile ID；
- 消息数量；
- 更新时间。

### 影响

- Profile 隔离只覆盖正文访问，没有覆盖元数据；
- Session ID 如果包含任务名或项目名，会泄露工作内容；
- 多用户或共享设备环境下尤其明显。

### 根因

Session 创建时已经把 `profile_id` 持久化到 `sessions` 表，Agent 直接恢复时也会
校验 Session 的 Profile。但列表是一条独立的读取通路，它的方法签名为：

```text
list_sessions(limit=20)
```

方法根本不接收 Profile，SQL 也没有 `WHERE s.profile_id = ?`。CLI 只能调用这个
全局查询，并把返回的每一行原样打印。

这个问题说明“阻止恢复其他 Profile 的正文”不等于“完成 Profile 隔离”。
Session ID、消息数和活动时间同样是需要隔离的数据。

### 解决方案

`SessionDB.list_sessions()` 现在把 `profile_id` 定义为必填的仅关键字参数：

```python
list_sessions(*, profile_id: str, limit: int = 20)
```

具体保证如下：

- 调用者如果遗漏 Profile，会立即得到类型/参数错误，不再默认执行全局查询；
- Profile ID 在进入 SQL 前使用与 Agent、Memory 相同的规则规范化；
- SQL 在 `GROUP BY`、排序和 `LIMIT` 之前执行 `WHERE s.profile_id = ?`；
- `message_count` 只会为当前 Profile 已选中的 Session 聚合；
- CLI 的 `--list-sessions` 必须把 `config.profile.id` 传入存储层，不再拿到其他
  Profile 的行后才在显示层过滤。

这里没有在 `_print_sessions()` 中写 `if session.profile_id == current_profile`的补丁。
显示层过滤意味着敏感元数据已经离开存储边界，其他新调用者也容易忘记过滤；
而且如果先执行全局 `LIMIT 20` 再过滤，其他 Profile 的新 Session 还可能把当前
Profile 的 Session 挤出列表。在 SQL 查询边界强制作用域才是完整逻辑。

### 验证证据

修复前在同一个真实 SQLite 数据库中创建 Alice 和 Bob Session，以 Alice 视角查询：

```text
configured_profile：alice
visible：
  bob-client-secret, profile=bob, messages=1
  alice-private-project, profile=alice, messages=1
```

修复后重新运行真实查询：

```text
list_sessions(profile_id="alice")
  → alice-private-project

list_sessions(profile_id="bob")
  → bob-client-secret
```

两个结果的 Session ID、Profile、消息数和时间元数据均不交叉。

自动化测试还在同一数据库中创建两条 Alice Session 和一条更新的 Bob Session，
确认 `limit=1` 在 Profile 过滤之后执行，Alice 仍可以看到自己最新的一条 Session。
CLI 真实渲染结果包含两条 Alice Session，不包含 `bob-client-secret` 或 `profile=bob`。

旧 Schema v3 数据库迁移后的 Session 仍正确归入 `default` Profile，并可通过
`list_sessions(profile_id="default")` 查看。全量自动化回归为 `138/138 PASS`。

### 当前状态

已于 2026-08-24 将 Profile 作用域下沉为 Session 列表查询的必填存储契约，并通过
真实多 Profile 数据库、SQL Limit 顺序、CLI 渲染和旧数据迁移回归。REAL-011 已关闭。

## REAL-012：Provider 瞬时故障一次就会中断任务//这里需要再完善一下

### 通俗描述

如果网络只抖动一次，第二次请求原本可以成功，当前 Agent 仍然不会再试。

### 实测结果

故障 Provider 被设置为：

```text
第一次调用：抛出临时错误
第二次调用：可以返回 RECOVERED
```

实际结果：

```text
Provider 调用次数：1
任务直接抛出 ProviderError
第二次成功机会没有被使用
```

### 影响

- 短暂网络抖动会直接打断任务；
- 没有备用 Provider 或备用模型；
- 没有针对限流、超时和临时服务错误的区别处理；
- 长任务接近完成时也可能因为一次瞬时错误整体中断。

### 根因

`OpenAICompatibleProvider._request()` 原来只执行一次 HTTP POST。它会把 HTTP、URL、
超时和其他传输异常全部转换为同一个 `ProviderError`，然后立即向上抛出。

Agent 的 Provider 调用层只会记录 `provider.request_failed`，也会原样重新抛出：

```text
HTTP/Network 故障
→ ProviderError
→ provider.request_failed
→ 本轮终止
```

最根本的问题不是缺少一个通用 `try/except`，而是错误丢失了“是否可重试”
语义。如果在 Agent 层捕获所有 `ProviderError` 都重试，401 密钥错误、400 请求错误、
非法 JSON、空响应或 Summary 违规返回 Tool Call 也会被反复发送，既不会自愈，
又浪费 Token 和时间。

### 解决方案

重试策略现在位于掌握 HTTP 语义的 Provider 传输层，普通对话和 Summary 请求
共用同一套逻辑。

可重试的错误是：

- DNS/连接等 `URLError`（TLS 证书校验失败除外）；
- 请求超时和传输层 `OSError`；
- HTTP `408 Request Timeout`；
- HTTP `425 Too Early`；
- HTTP `429 Too Many Requests`；
- HTTP 5xx 临时服务错误。

明确不重试的错误是：

- 400/401/403/404/422 等客户端、认证和配置错误；
- TLS 证书校验失败；
- HTTP 200 后的非法 JSON 或非法 Chat Completions 结构；
- Summary 返回 Tool Call、空文本等已收到的语义违约。

配置新增：

```yaml
provider:
  max_attempts: 3
  retry_backoff_seconds: 0.5
```

`max_attempts` 包含首次请求，被限制在 1–10 次。后续尝试使用有限指数退避：

```text
0.5s → 1.0s → 2.0s ...
```

请求一旦成功，`ProviderResponse.attempt_count` 会携带真实尝试数，
`provider.request_completed` 事件也记录该值。如果有限次数全部失败，最终
`ProviderError` 会记录 `attempts` 和 `retryable=true`，Agent 的失败事件同样保留这些
诊断元数据。

工具副作用边界保持不变：Provider 的多次尝试只是发送同一份模型请求。只有在
某次请求成功返回、JSON 已解析且 Tool Call 已验证后，Agent 才会执行本地 Tool
Handler。失败的 HTTP 尝试不会创建 Tool Journal，也不会重复本地副作用。

需要说明：超时前 Provider 远端可能已经完成推理并计费，通用 OpenAI-compatible
接口无法证明或取消这次远程计算。因此重试能保证不重复本地工具副作用，
但不承诺只产生一次远程模型费用。这也是限制尝试次数而不是无限重试的原因之一。

### 验证证据

使用真实本地 HTTP Server 实现 OpenAI-compatible `/chat/completions`，不是只让一个
Python Fake Provider 抛异常。服务端响应顺序为：

```text
第 1 次：HTTP 503 {"error":{"message":"temporarily unavailable"}}
第 2 次：HTTP 200 Assistant(content="RECOVERED")
```

真实 Agent 结果：

```text
Agent 答案：RECOVERED
HTTP 请求数：2
两次 request body 完全相同：true
provider.request_completed.attempt_count：2
```

真实工具循环的 HTTP 响应顺序为 `503 → Tool Call → final answer`，结果：

```text
HTTP 请求数：3
Tool Handler 执行数：1
Agent 答案：tool completed
```

不可重试路径确认 HTTP 401 只发送 1 次，HTTP 200 但非法 JSON 也只发送 1 次。
持续 HTTP 503 的有限次数测试确认共尝试 3 次，退避序列为 `0.25s, 0.5s`，
随后如实抛出 `HTTP 503: overloaded after 3 attempts`。

Provider 与 Config 专项测试为 `13/13 PASS`，全量自动化回归为 `142/142 PASS`。

### 当前状态

已于 2026-08-24 完成 Provider 传输错误分类、有限指数退避和尝试数可观测性的
根因修复，并通过真实 HTTP 恢复、工具单次副作用、不可重试错误和全量回归。
REAL-012 已关闭。

## REAL-013：持久 Context Compression 默认没有启用

### 通俗描述

持久上下文压缩虽然已经开发完成，但默认配置是关闭的：

```yaml
compression:
  enabled: false
```

普通用户直接运行项目时，不会自动使用持久语义摘要。

### 影响

- 长 Session 默认仍然主要依赖临时 API 副本裁剪；
- 跨进程 Resume 没有自动生成的稳定语义交接；
- 用户可能以为新能力已经生效，实际只有手动压缩或修改配置后才使用；
- 原来的长会话痛点在默认配置下仍可能出现。

### 根因

持久压缩在阶段 14.3 刚上线时刻意采用“默认关闭，真实验证后再开启”的
分阶段策略。这个选择在当时是安全的，但后续已经完成了：

- 超长 Summary 输入分层切分；
- 密钥脱敏；
- 负节省/低收益候选拒绝；
- 压缩事务回滚；
- 可续期并发租约；
- Summary 失败后保留原历史、Cooldown 和 Anti-thrashing；
- Resume 后重用持久 Summary；
- 真实长 Session 自动触发。

但产品默认没有随验证结果一起升级，而且关闭状态同时存在三个层次：

```text
仓库 config.yaml                  compression.enabled: false
配置解析缺省值              default=False
CompressionPolicy 类的缺省值   enabled=False
```

因此即使用户删除了 YAML 中的开关，配置解析仍会默认关闭；即使绕过 CLI
直接构造 Policy，类的默认也仍然关闭。这是阶段性上线开关在验证完成后没有
被正式推进的交付闭环问题。

### 解决方案

三个默认层现在统一表达同一个产品契约：

```text
仓库 config.yaml                  compression.enabled: true
配置解析缺省值              default=True
CompressionPolicy 类的缺省值   enabled=True
```

用户仍可以显式退出：

```yaml
compression:
  enabled: false
```

默认开启不等于每轮都调用 Summary Provider。仍然只有在同时满足以下条件时才尝试：

- 使用持久 `SessionDB`；
- 估算活动上下文达到可用输入窗口的 `threshold_ratio`，当前默认为 75%；
- Session 不在失败 Cooldown 中；
- Anti-thrashing 没有因连续低收益或 fallback 暂停；
- 存在既不属于首部保护轮次、也不属于最新 tail 的完整中间历史。

安全失败逻辑没有因默认开启而改变：Summary Provider 失败时，活动历史不会
软归档，不会写入半份 Summary；Agent 随后仍可以用原历史请求主 Provider。低收益
候选也会在写入之前拒绝。

### 验证证据

使用仓库真实 `config.yaml`、真实 SQLite SessionDB 和 120 轮长历史，修复前结果：

```text
config_enabled：false
估算上下文：62,951 tokens
自动阈值：45,000 tokens
压缩状态：below_threshold
Summary Provider 调用：0
```

注意历史已明显超过阈值，`below_threshold` 实际是原实现把“开关关闭”和“未达
阈值”共用了一个状态名称，Summary 没有运行。

修复后使用完全相同的配置加载和长历史：

```text
config_enabled：true
估算上下文：62,951 tokens
压缩状态：committed
Summary Provider 调用：1
compression_runs：1 committed
活动消息：240 → 48
```

进一步的真实 Agent 自动链路测试没有手动调用 `compress(force=True)`，而是向恢复后的
Agent 发送 `latest real request`。结果是 Agent 在主 Provider 之前自动提交压缩，主 Provider
收到一份 `[CONTEXT COMPACTION]` Summary，最后一条仍是真实用户请求，并正常回答
`continued after default compression`。

显式 `enabled: false` 配置测试会返回真实的 `disabled` 状态且不调用 Summary。
已有 Summary 失败回归确认

## REAL-015：推理模型可能耗尽动态摘要额度，导致持久化压缩失败

### 通俗描述

持久化压缩并不总会把配置中的 `max_output_tokens: 2000` 全部交给摘要模型。
压缩器还会根据压缩后必须节省的 token 数动态缩小摘要输出额度。在额度很小时，
当前 `deepseek-v4-pro` 可能把全部额度用于内部 reasoning，最终没有返回正文。

Harness 不会把 reasoning 当作最终摘要；当响应既没有正文也没有 Tool Call 时，
Provider 会抛出 `ProviderError`，因此本次持久化压缩失败。

### 真实复现过程

使用仓库当前真实 `config.yaml`、`.env` 中已配置的真实 API、真实
`OpenAICompatibleProvider` 和临时 SQLite `SessionDB`：

1. 创建包含首部轮次、中间待压缩轮次和超长尾部轮次的三轮 Session；
2. 使用当前默认压缩策略执行强制持久化压缩；
3. 压缩器根据最低节省要求，将本次摘要请求动态限制为 57 tokens；
4. 将真实 Provider 返回值做脱敏后，只检查正文长度、reasoning 长度和结束原因。

实际结果：

```text
压缩前估算：14,394 tokens
摘要请求 max_tokens：57
响应 content 长度：0
响应 reasoning_content 长度：300
finish_reason：length
completion_tokens：57

compression status：failed
error_type：ProviderError
archived：0
活动消息：仍为原来的 6 条
```

为了确认问题与小额度有关，还对同一真实 Provider 做了两次直接摘要测试：

```text
max_tokens=512：content 长度 475，finish_reason=stop，成功
max_tokens=128：content 长度 0，reasoning_content 长度 714，
                finish_reason=length，失败
```

这证明当前模型并非完全不能生成摘要，而是在较小输出预算下可能先耗尽 reasoning
额度，来不及生成可提交的正文。

### 对原问题描述的校正

“三轮 Session、压缩前约 7,306 tokens、执行后出现 ProviderError”在当前默认配置下
没有复现。当前 `tail_tokens=12000`，使用约 7,362 tokens 的真实三轮持久 Session
执行强制压缩，结果为：

```text
status：no_middle
archived：0
error_type：None
```

因为整段历史都落在受保护的最新 12,000-token tail 中，压缩器没有中间历史可以
摘要，也没有调用 Provider。因此 REAL-015 只记录上面已经真实复现的 14,394-token
场景，不把 7,306-token 场景记作已确认事实。

### 根因

- `provider.py` 的摘要请求把压缩器给出的动态额度直接写入 `max_tokens`；
- `context_compression.py` 的 `_summary_token_budget()` 会基于目标体积和最低节省量
  将 2,000-token 配置上限继续缩小；
- 原实现错误地把“摘要应当占用的目标体积”和“模型生成过程的硬上限”当成同一
  个数。普通模型可能直接生成正文，但 reasoning 模型的内部推理和可见正文共享
  这个硬上限，因此一个为了满足压缩收益而计算出的较小目标会先截断推理过程；
- Harness 只接受正式 `content` 是正确的语义边界，不能把模型内部 reasoning
  直接冒充持久化摘要。真正需要修复的是预算与模型能力适配，而不是把 reasoning
  当正文保存。

### Hermes 参考与取舍

重点检查了 Hermes 的 `agent/context_compressor.py`。Hermes 会计算 Summary 目标预算，
并把 `Target ~N tokens` 写入摘要 Prompt，但摘要调用刻意不传 `max_tokens`。其源码注释
说明：硬输出上限会让 thinking 模型先消耗额度，产生截断或 thinking-only Summary。

mini-harness 采用了相同的核心原则，但没有机械照搬整个压缩器：

```text
摘要目标长度       → Prompt 中的语义约束
Provider 生成空间   → 不使用同一个数做 wire-level max_tokens 硬截断
是否允许持久化     → 继续由 mini-harness 的真实节省率和 SQLite 事务门禁决定
```

这样保留了 mini-harness 已有的“压缩必须真的节省空间”契约。

### 解决方案

1. `OpenAICompatibleProvider.summarize()` 不再把动态摘要目标写入请求体的
   `max_tokens` 或 `max_completion_tokens`，给 reasoning 模型足够空间完成推理并
   生成正式 `content`；
2. 压缩器把动态预算写入 Prompt，要求模型将最终可见摘要控制在大约 N tokens，
   因而预算仍然参与摘要质量和体积控制；
3. 删除“模型返回过长时直接从中间截断，然后继续提交”的旧逻辑。完整摘要必须
   进入现有的 `estimated_after_tokens` 和最低节省率检查；
4. 如果完整摘要太长，结果如实返回 `rejected / InsufficientCompressionSavings`，
   原活动历史保持不变；只有完整摘要满足收益契约时才执行原子的软归档事务；
5. reasoning 仍然不会被保存或冒充摘要，空正文仍然是 Provider 失败。

这不是针对 `deepseek-v4-pro` 名称写特判，而是修复了所有“内部推理与可见正文
共享生成额度”的 Provider/模型类别。

### 影响

- 当前默认 Provider 可以正常聊天和调用工具，但持久语义压缩在动态预算较小时
  不可靠；
- 压缩失败后历史不会被归档，长 Session 仍可能继续增长；
- 自动压缩会进入既有失败 Cooldown，短时间内不会持续请求 Provider；
- 失败路径保持了数据安全：本次真实测试中没有归档原消息，也没有写入半份摘要。

### 当前状态

已于 2026-08-24 完成根因修复。真实 DeepSeek API 验证结果如下：

Hermes针对这个问题，最关键的处理是：

> 摘要预算只作为提示，不再作为API的硬输出上限。

### mini-harness当前的问题

mini-harness大致是：

```
计算摘要最多只能有100 Token
→ 请求里发送 max_tokens=100
→ reasoning用了100 Token
→ 正文content没有额度
→ content为空
→ 压缩失败
```

这里的“摘要目标长度”和“模型最大输出额度”被当成了同一个东西。

### Hermes的处理

Hermes也会计算`summary_budget`，比如希望摘要大约500 Token，但它只把这个数字写进Prompt：

```
Target ~500 tokens.
```

发送摘要请求时，Hermes刻意不传`max_tokens`：

```
call_kwargs = {
    "task": "compression",
    "messages": [...],
    # 没有 max_tokens
}
```

源码注释明确说明，不能用硬输出上限截断摘要：[context_compressor.py (line 2101)](D:/learning/hermes-agent/hermes-agent-main/agent/context_compressor.py:2101)

因此流程变成：

```
希望正文约500 Token
→ Prompt告诉模型“目标约500 Token”
→ API不限制模型只能输出500 Token
→ reasoning可以使用额外输出空间
→ 最后仍有空间生成正文
```

换句话说，Hermes把两个概念分开了：

```
摘要目标长度
→ 控制最终摘要应该多精炼
→ 使用Prompt软约束

模型输出总额度
→ reasoning和正文共享的物理空间
→ 不设置过小的硬上限
```

### Provider兼容处理

Hermes的辅助模型调用层默认也不传`max_tokens`，让模型使用Provider原生输出上限。[auxiliary_client.py (line 6328)](D:/learning/hermes-agent/hermes-agent-main/agent/auxiliary_client.py:6328)

只有某些协议强制要求该字段，例如Anthropic兼容接口，才会保留必要的输出额度，而不会根据“必须节省多少Token”动态压到几十个Token。

### 正文仍然为空怎么办？

Hermes不会把空正文当成成功摘要。

它会检查：

```
if not content.strip():
    raise RuntimeError(...)
```

然后：

1. 不保存空摘要；
2. 不让空摘要替换原上下文；
3. 如果使用的是独立摘要模型，切换到主模型再生成一次；
4. 仍然失败则进入压缩失败或本地fallback流程；
5. 认证和最终网络故障会直接中止压缩并保留原会话。

相关检查在 [context_compressor.py (line 2133)](D:/learning/hermes-agent/hermes-agent-main/agent/context_compressor.py:2133)。

### reasoning内容怎么处理？

Hermes不会把reasoning直接当成压缩摘要。摘要必须有正式的`content`正文。

如果正文里混入：

```
<think>……</think>
```

Hermes会删除这些推理块，只保存最终摘要，防止推理内容进入长期上下文并不断膨胀。

所以Hermes的完整方案是：

```
摘要长度使用软约束
＋ 不设置过小的API硬输出上限
＋ 空正文严格判失败
＋ 摘要模型失败时换主模型
＋ 推理内容不写入长期摘要
```
